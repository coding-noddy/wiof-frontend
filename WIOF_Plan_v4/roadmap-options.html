Two things worth resolving regardless of path

Neither is a reason to stop and fix everything before deciding direction — but any path you choose will run cleaner once these are settled.

Admin role can self-escalate on profile creation Security

firestore.rules line 44 allows create on users/{userId} with only an ownership check — no restriction on which fields the document may contain. A user creating their own profile document for the first time could set role: 'admin' directly, since the field-restriction logic (isValidOwnProfileUpdate) only applies to updates, not creates.

This is the exact scenario the Foundation Hardening Plan's §3.1 describes. Fix is contained: extend the create rule with the same field allow-list, or move admin authority off the user document entirely (see the spec-conflict note below).

Poll responses expose email/IP to any reader Privacy

firestore.rules lines 157–171: the Polls collection is publicly readable (allow read: if true) and stores email, ip4, and ip6 in the same document as the vote itself. Any visitor can read every respondent's email and IP alongside their answer.

Plan v4 §3.3 calls for splitting public aggregate results from private raw responses. That split hasn't happened yet.

Two competing specs for the same phase of work Process

user-engagement-layer and user-engagement-foundation both describe a full accounts/bookmarks/activity system for the same phase, with incompatible data models — different collection names (user_saved_content vs saved_content), different activity log names, and different admin-authority designs (a role field vs a separate admins collection).

The deployed rules and every newer spec (daily-visit-tracking, journey-section-navigation, video-watch-tracking, user-settings-page) match user-engagement-layer, so user-engagement-foundation looks like a stale duplicate. One nuance: its admins-collection idea is the more defensible design and worth reusing when the role-escalation fix above gets built, even though the rest of that spec should be retired.

Four paths forward

Not mutually exclusive in the long run — the question is what leads.

Finish the Foundation

~2–3 wks

Close the two findings above, move admin authority onto a trusted source (custom claims or the admins-collection pattern), split public poll results from raw responses, roll out App Check in monitoring mode, add Firestore-emulator rules tests to CI, retire the duplicate spec.

Why now — everything built after this inherits whatever trust model exists today. It's a rules change now; it becomes a migration later.

Trade-off — no visible new capability for the effort spent.

Start the Action Engine

~5 wks

Structured daily actions (daily_actions + completion records), admin authoring, streak-linked completion UI, first honest impact estimates with a documented methodology.

Why now — both vision docs name this as WIOF's identity feature ("One Small Step"), and the plumbing it needs — activity_log, streaks, My Journey — already exists.

Trade-off — action completions and impact numbers would sit on an auth model with a known escalation hole until it's patched.

Brand & Experience Alignment

~4–6 wks

Design tokens from the approved brand guide (the palette this very document uses), Aleo/Noto Sans typography rollout across nav, cards and buttons, IA cleanup, accessibility pass across public/authenticated/admin surfaces.

Why now — v4 explicitly sequences this before major new features, and engagement work has already outpaced it — it's the largest process debt on the board.

Trade-off — delays the visible new capability (Actions, Passport) stakeholders may be expecting next.

One way to combine them

A possible ordering if you want a single thread to follow — not the only valid one.

Weeks 1–3
Foundation close-outBoth findings, custom-claims or admins-collection migration, spec cleanup. Small and contained — worth doing before anything else touches auth or impact data.
Weeks 4–9
Brand alignment, in parallel with early Action Engine designDesign tokens and IA work don't block backend/data-model work on the Action Engine — they can run side by side if you have (or bring on) design capacity, per the master plan's "part-time designer" assumption.
Weeks 10–15
Action Engine shipsStructured actions, completion, first impact numbers — now sitting on a hardened auth model and an aligned visual system.
Week 16+
Planet PassportOnly once the Action Engine is producing trustworthy events to derive achievements from — per v4's explicit dependency chain.

If you don't have parallel design capacity, Brand Alignment and the Action Engine become sequential, not parallel — worth naming explicitly rather than assuming.
